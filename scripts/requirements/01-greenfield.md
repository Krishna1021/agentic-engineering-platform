Build a working URL shortener from scratch. Use Java 17, Spring Boot, PostgreSQL, Flyway and plain Groovy Gradle DSL. Generate complete source, executable tests and Markdown documentation. Do not use a fixed demonstration scaffold.

Acceptance criteria:
1. POST /api/shorten accepts {"url":"https://example.com/path"} and returns an eight-character case-sensitive Base62 shortCode. GET /{shortCode} returns HTTP 302 with the exact destination in Location. Unknown codes return 404.
2. Accept absolute HTTP/HTTPS destinations with a valid host. Reject blank, missing, malformed, unsupported-scheme and hostless URLs with a consistent JSON 400 response. Use a documented 2048-character destination limit.
3. Persist mappings across restart. Generate codes with bounded retries. Insert atomically, and retry only code uniqueness collisions; never overwrite an existing mapping. Concurrent collisions must preserve the original destination. Distinguish database unavailability from collision exhaustion in error handling.
4. Record a successful redirect count per short code and UTC date. GET /api/links/{shortCode}/analytics returns totalRedirects and dailyCounts. Unknown codes return 404. Updates must be atomic under concurrency. Failed/unknown redirects do not count. Do not store IP addresses, user agents or visitor identifiers. Analytics write failure must not prevent a known destination redirect; document this best-effort trade-off.
5. Supply Flyway schema/migrations, OpenAPI descriptions, environment-based database configuration and a health endpoint without public sensitive details. No embedded database credentials.
6. Enable JUnit Platform in Groovy Gradle. Include unit tests and integration tests, deterministic collision-then-success/exhaustion tests, concurrent mapping safety, destination validation, creation/redirect/404, daily counts and concurrent increments, and analytics failure behavior. Isolate test database configuration from production. Include a separately selectable real PostgreSQL suite and document its external prerequisites; the offline default suite must not require nested Docker or network access.
7. Validation must execute tests, not just compile. Record test counts, failures and skipped tests. Do not claim PostgreSQL validation if only a lightweight database ran. Use worker-cached dependencies and explicitly report unavailable dependencies instead of substituting demo success.
8. Document architecture, plan/rationale, API/schema, setup, acceptance-criterion-to-test mapping, assumptions, risks, trade-offs, validation evidence and remaining limitations under docs/. Prepare a reviewable local output; do not deploy or publish.
